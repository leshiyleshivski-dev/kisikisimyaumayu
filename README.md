# Кисикисимяумяу

Десктопный кликер про котиков для Windows на CustomTkinter. Внутри кликера
спрятаны девять «секретных модулей» — вспомогательных экранов для мини-игр
GTA V, которые открываются рецептами в кормилке. Девятый, POKER ADVISOR,
единственный ничего не нажимает: он читает покерный стол и подсказывает ход.

Это единственный обзорный документ проекта: устройство, правила и требования
к ресурсам собраны здесь. Узкие инженерные записи вынесены отдельно и
перечислены в конце.

## Быстрый старт

```powershell
python kiski_clicker.pyw
```

Равнозначный способ во время разработки:

```powershell
python -m kisiki
```

### Зависимости

Файла `requirements.txt` в проекте нет, ставим руками:

```powershell
pip install customtkinter numpy mss opencv-python
```

Проверено на Python 3.13, CustomTkinter 6.0.0, numpy 2.5, mss 10.2, OpenCV 5.0.
Pillow не нужен и намеренно не используется: картинки грузятся средствами Tk,
чтобы не тащить лишнюю зависимость в собранный `.exe`.

Проект рассчитан только на Windows: `core.py` работает напрямую с `user32`,
`winmm` и `kernel32` через `ctypes`.

## Правила архитектуры

Зависимости идут только сверху вниз:

```text
kiski_clicker.pyw → kisiki.app → kisiki.modules → kisiki.core
                                  volt.module → volt.* mixins
```

- `core.py` ничего не импортирует из экранов приложения.
- Игровые модули могут использовать `core.py`, но не друг друга.
- Решатели Volt не создают окон. Они добавляют специализированные методы
  контроллеру `ElectricianModule` через mixin-классы.
- `miner_vision.py`, `blackjack_vision.py`, `poker_vision.py`, `poker_math.py`,
  `poker_ranges.py`, `poker_preflop.py`, `poker_postflop.py`,
  `poker_journal.py` и `poker_stats.py` не создают окон и не отправляют
  ввод: первые три анализируют кадр, следующие четыре считают числа и карты, а
  последние два хранят сыгранные раздачи и считают по ним статистику стола.
  Жизненный цикл, фокус GTA и статистика сессии принадлежат `miner.py`,
  `blackjack.py` и `poker.py`.
- `app.py` отвечает за создание экранов и переключение между ними.

Такой порядок не создаёт циклических импортов и позволяет тестировать
компьютерное зрение без запуска окна CustomTkinter.

### Куда вносить изменения

| Что меняем | Где |
| --- | --- |
| Цвета, пути к ресурсам, WinAPI, клавиатурный ввод | `kisiki/core.py` |
| Главный экран, кормилка, рецепты, навигация | `kisiki/app.py` |
| Цены, доход, вылазки, достижения | `kisiki/clicker.py` |
| Логика конкретного секретного экрана | файл в `kisiki/modules/` |
| Новый сценарий электрика | новый файл в `kisiki/modules/volt/`, подключение — в `module.py` |
| Состав еды и рецептов | `food_catalog.py` |

Не возвращаем алгоритмы распознавания в `kiski_clicker.pyw` или `app.py`: эти
файлы не склад общей логики.

## Игровые системы

**Котики.** Девять играбельных котиков в `CATS` (`kisiki/core.py`), у каждого
свой прогресс, уровень и магазин улучшений. `COMING_SOON_CATS` — карточки
«в разработке» на главном экране, у них нет ни картинок, ни логики.

**Экономика** (`kisiki/clicker.py`): улучшения на клик и автодоход, декор с
глобальными процентными бонусами, вылазки (2/10/30 минут), ежедневные задания
со streak-наградой, достижения, офлайн-доход с потолком в 8 часов.

**Рецепты и секретные модули.** В кормилке нужно скормить конкретному котику
три блюда в точном порядке — тогда откроется секретный экран. Источник правды
— `SECRET_RECIPES` в `food_catalog.py`:

| Модуль | Котик | Последовательность |
| --- | --- | --- |
| RLT CONTROL | Крупье | Рыбка → Тунец → Лосось |
| PHONE BEAT | Звонок | Молоко → Сосиска → Лакомство |
| BRICK TIMING | Кирпич | Куриная ножка → Морковь → Тыква |
| VOLT GRID | Вольт | Сыр → Креветка → Секретное блюдо |
| ORE HUNT | Кварц | Сухой корм → Бургер → Молоко |
| RACE BETTOR | Фаворит | Морковь → Лакомство → Рыбка |
| SLOT SPINNER | Семёрка | Пицца → Пончик → Мороженое |
| BLACKJACK RUN | Туз | Суши → Арбуз → Клубника |
| POKER ADVISOR | Блеф | Тунец → Пончик → Секретное блюдо |

Книгу рецептов можно открыть напрямую: пять нажатий на заголовок
«КИСИКИСИМЯУМЯУ» в течение четырёх секунд.

### RACE BETTOR — кот «Фаворит»

Модуль автоматизирует ставки в Inside Track и останавливается только после
заданного числа **побед**, а не попыток. Например, цель `4` означает, что
проигрыши будут учтены в статистике, но цикл продолжится до четвёртой победы.

Перед запуском нужно сесть за терминал скачек и вручную оставить желаемый
размер ставки. Дальше модуль работает сам:

1. Открывает список гонщиков клавишей `F` и находит строку с коэффициентом
   `2/1` средствами компьютерного зрения.
2. Плавно перемещает настоящий курсор и один раз выбирает найденного гонщика.
   Если карточка ставки уже открыта после предыдущего заезда, повторно строку
   `2/1` не нажимает.
3. Нажимает мышью «Сделать ставку» в случайный момент — примерно при остатке
   от 27 до 15 секунд. Размер ставки модуль не изменяет.
4. Проверяет подтверждение, распознаёт зелёную победу или красный проигрыш и
   запускает следующий круг, пока цель не выполнена.

`F9` запускает и останавливает цикл, `F11` выполняет аварийную остановку.
Во время кликов приложение ненадолго переводит фокус в GTA, а затем возвращает
предыдущее окно и курсор. Если строка `2/1`, карточка или результат не
распознаны уверенно, модуль не кликает вслепую: повторяет поиск либо безопасно
останавливается по тайм-ауту.

### SLOT SPINNER — кот «Семёрка»

Модуль автоматизирует слот-машину и, как RACE BETTOR, останавливается по числу
**побед**, а не вращений. Например, цель `4` продолжает цикл после любого числа
проигрышей и завершает его только после четвёртого подтверждённого выигрыша.

Перед запуском нужно сесть за слот-машину, вручную выставить ставку в GTA и
указать в модуле только число побед. Помощник не нажимает стрелки и никак не
меняет выбранный размер ставки. После `F9` каждое вращение запускается клавишей
`F`. При первом `F9` помощник сначала переводит фокус в GTA и сразу отправляет
первый `F`, даже если стартовый кадр интерфейса распознался неуверенно; повторно
нажимать `F9` или запускать слот вручную не нужно. Примерно через 1,7–2,4
секунды после появления результата запускается
следующее вращение — ждать исчезновения уведомления не требуется. Оставшееся
на экране старое уведомление игнорируется до очистки области и не может быть
засчитано повторно. Зелёное уведомление
«Вы выиграли … фишек!» засчитывается как победа, красное — как вращение без
победы. Следующий спин начинается только после исчезновения прошлого
уведомления. Если интерфейс слота или результат не распознаны, модуль безопасно
останавливается без дополнительного нажатия. `F11` — аварийная остановка.

### BLACKJACK RUN — кот «Туз»

Третий модуль-лудоман тоже считает **победы**, а не попытки: цель `15`
означает, что цикл продолжится сквозь любое число проигранных раздач и
остановится только после пятнадцатой победы.

Перед запуском нужно сесть за стол блэкджека и стрелками выставить желаемый
размер ставки. Дальше по `F9` модуль ведёт раздачу сам:

1. На экране ставки нажимает `Enter` — «Сделать ставку». Стрелки `←` и `→`
   он не трогает, поэтому размер ставки остаётся ровно тем, что выставил ты.
2. Читает строку «У вас [N] , У дилера [M]». Это подпись интерфейса по центру
   экрана, а не надпись в мире, поэтому движение камеры ей не мешает. Ход
   делается только после трёх одинаковых чтений подряд: один кадр может
   испортить рука дилера или пролетевшая бабочка.
3. Играет по базовой стратегии: `Enter` («Ещё») до 11, `Пробел`
   («Достаточно») от 17, а на 12–16 смотрит на карту дилера. Пока карта
   дилера закрыта (`[0]`), добирает до семнадцати.
4. Ждёт уведомление о результате: зелёное — победа, красное — раздача без
   победы. Если раздача закрылась совсем без уведомления (например ничья),
   модуль засчитывает её как раздачу без победы и идёт дальше. Плашка висит
   на экране ещё секунд пять и захватывает начало следующей раздачи, поэтому
   уже посчитанное уведомление игнорируется до очистки области и не может
   быть засчитано дважды. Ждать его исчезновения модуль не станет: стол
   открывает ставку сразу, и пауза съедала бы почти всё окно ставки.

`Дабл` модуль не нажимает: ставка не должна меняться сама. Сплит стол не
предлагает вовсе, поэтому пар в таблице тоже нет.

**Мягкие руки.** Игра показывает одно число вместо карт, но туз в Majestic
всегда приходит как `11`, а счёт во время раздачи растёт по одной карте.
Этого хватает, чтобы `HandReader` отличил мягкую руку от жёсткой:

- первая карта `[11]` или прибавка ровно на 11 — в руке появился туз,
  который сейчас считается за одиннадцать;
- если после добора счёт не вырос, туз упал в единицу и рука стала жёсткой:
  мягкие 16 (A+5) плюс десятка снова показывают 16.

Мягкую руку перебрать нельзя, поэтому она играется отдельной строкой: до
восемнадцати добираем всегда, а на мягких восемнадцати встаём только против
слабой карты дилера. Без этого модуль вставал бы на A+6 и на двух тузах —
примерно каждая тринадцатая раздача игралась бы заведомо неправильно.

Фаза стола определяется по правому столбцу подсказок: две тёмные панели
(«РАЗМЕР СТАВКИ» и «ЭТА СТАВКА») — идёт ставка, панель «ВРЕМЯ» под белой
кнопкой — идёт ход. Цветное пятно само по себе результатом не считается:
опорой служит тёмная плашка уведомления, а цвет читается только у её правого
края, где игра рисует полоску результата. Иначе зелёное сукно и красные фишки
давали бы ложные победы.

Полоску нельзя искать отдельным цветным пятном: зелёная полоска победы
вплотную примыкает к такому же зелёному сукну и слипается с ним в одно
широкое пятно. Красная так не слипается — из-за этого проигрыши считались, а
победы молча уходили в «раздачи без выигрыша».

`F9` запускает и останавливает цикл, `F11` — аварийная остановка. Если стол
или счёт руки не распознаны, модуль не нажимает вслепую и останавливается по
тайм-ауту.

### POKER ADVISOR — кот «Блеф»

Единственный модуль, который **ничего не нажимает**. Рецепт кота «Блеф»
открывает экран `kisiki/modules/poker.py`: он смотрит на стол и советует ход,
а кнопки жмёт человек.

`kisiki/modules/poker_math.py` оценивает силу руки, считает эквити перебором
и шансы банка и выдаёт совет — фолд, чек, колл, бет или рейз, вместе с
названием собранной комбинации и размером ставки. Совет занимает от 3 до
300 мс, а игра даёт на ход около пятнадцати секунд. Порог «рука стоит ставки»
считается от числа соперников: против одного средняя рука берёт половину
раздач, против пятерых — шестую часть, и одним числом эти столы не мерить.

**До флопа считает не перебор, а таблица.** Перебор сравнивает руку со
случайными картами соперника, и 3♠9♦ выходит у него сорок процентов — выше
шансов банка, значит «колл». На записи `6.mp4` помощник так принял двадцать
префлоп-решений подряд и ни разу не сказал «фолд»: играл 9♠3♠, J♣6♦, 2♣9♥.
Проигрываются такие руки не до флопа, а после — каждую приходится доигрывать
позади и без сильной пары. Против настоящего диапазона у тех же рук не сорок
процентов, а двадцать пять — тридцать.

`kisiki/modules/poker_preflop.py` держит две книжки и выбирает между ними по
глубине стека в блайндах. Глубже пятнадцати ставок — таблица открытия: что
открывать повышением с каждой позиции, чем отвечать на чужое повышение и чем
повышать в ответ. Мельче — только олл-ин или пас: доигрывать раздачу нечем,
постфлопа на такой глубине не существует. Стол на двоих — отдельная книжка,
там открывают две трети рук вместо трети.

Из большого блайнда таблица открытия пуста — он торговлю закрывает, а не
начинает. Но когда до него доходит компания лимперов, ход появляется, и до
разбора записи `8.mp4` его не было: на тузов против четверых зашедших
уравниванием совет был «чек». Формально верно — «открывать не стоит», — а по
делу лучшая рука в покере уходила в многосторонний флоп даром. Теперь у
большого блайнда против лимперов своя книжка: они вошли задёшево и с чем
попало, а банк можно забрать ещё до флопа.

Пуш-диапазоны заданы таблицей, а не выведены счётом выгоды, хотя такой счёт в
модуле есть. Счёт исходит из того, что соперник отвечает четвертью рук, — и
тогда олл-ин с 92o выходит выгоднее паса, потому что три раза из четырёх все
спасуют. Но отвечающий диапазон не стоит на месте: против того, кто идёт
ва-банк с чем попало, отвечают вдвое шире. Свести это в равновесие на лету
нельзя, и `shove_ev` остался объяснять совет, а не принимать его.

`kisiki/modules/poker_ranges.py` — общий фундамент: 169 стартовых рук, их сила
и запись диапазона привычной строкой вроде `77+, A2s+, KQo`. Плюс в этой записи
всегда наращивает младшую карту, а связки пишутся перечнем: `65s+` в разных
программах читают по-разному, и молча угадывать тут нечего. Сила посчитана
перебором 60 000 раздач на класс и сходится с известными числами — AA берёт у
случайной руки 85 %, AKs 67 %, 32o 32 %.

Тот же фундамент дал `equity_vs_range()` в `poker_math.py`: эквити против
диапазона, а не против двух случайных карт. Разница решает раздачи. На тёрне
4♣5♠7♣9♥ пара девяток с кикером «тройка» берёт у случайной руки 72 %, у
рейзящего диапазона — 15 %. Именно на этой руке в записи `6.mp4` ушёл стек:
помощник посоветовал ставить 2 400 при «эквити 73 %», соперник ответил
олл-ином, и у него оказалась та же тройка девяток с лучшим кикером.

**После флопа считает `poker_postflop.py`.** Диапазон соперника сужается
дважды: сперва по стартовой руке — до флопа доходят не со всем подряд, — потом
по борду, и второе важнее. Тот, кто повысил на тёрне, держит не «сильную
стартовую руку», а руку, которая попала в эти карты: 7-2 на борде 7-7-2 стоит
дороже, чем A-K мимо.

Сила на борде считается с учётом доборов, а не по готовой комбинации, иначе
флеш-дро оказалось бы в самом низу диапазона — хотя повышают с ним постоянно.
На ривере доборов нет и ответ точный, на тёрне перебираются все 44 карты, на
флопе их 990 и там идёт выборка.

Насколько сужать — говорит размер ставки в долях банка, каким он был до неё.
Ставка в четверть банка бывает с чем угодно, ставка в банк — почти всегда либо
с готовой рукой, либо с пустой. Поэтому диапазон ставящего не сплошной: к
верхушке добавляется доля блефа со дна. Без неё выходила ошибка, обратная
прежней: туз-хай против олл-ина брал ровно ноль, и на флопе 4♦3♠4♠ получался
фолд при шансах банка десять к одному.

Считаются два разных диапазона, и путать их нельзя. Соперник поставил — считаем
против того, **с чем ставят**, и решаем, окупается ли доплата. Не поставил —
против того, **кто ответит** на нашу ставку, и решаем, стоит ли ставить. И
узкий диапазон достаётся только тому, кто ставил: остальные за столом просто
ещё держат карты.

**Экран `ALL IN` / `FOLD`.** Когда доплата больше стека, повышать не на что, и
игра убирает ряд быстрых размеров, ползунок и саму кнопку повышения. Помощник
считал такой экран чужим ходом и молчал — семь раз из сорока в записи `6.mp4`,
и каждый раз на кону стоял весь стек. Отличается он тем, что правая нижняя
клетка пуста: ни ползунка, как на своём ходу, ни четвёртой кнопки, как у
преактива. Одной горящей кнопки `FOLD` мало — она горит на всех трёх экранах.

Сумму с такой кнопки раньше не удавалось прочитать под курсором: правило было
«слово первое, всё остальное — сумма», а в `ALL IN 4 500` первым словом уходит
`ALL`, и `IN` в число не складывалось. Теперь куски читаются с конца, пока
складываются в цифры.

На этом экране кнопка называет не всю чужую ставку, а то, что реально уйдёт из
стека. Числа два, и они разные: по тому, сколько **мы платим**, считаются шансы
банка, по тому, сколько **он поставил**, читается диапазон. Пока в чтение шла
обрезанная стеком сумма, ставка в банк выглядела ставкой в восьмую банка. И
чужой излишек сверх нашего стека вернётся ему — разыгрывается только та часть
банка, которую мы в состоянии уравнять.

**Позиция.** Метку `D` игра рисует у правого края панели игрока — залитый
малиновым квадратик 29 × 30. По ней `poker_vision.py` находит кнопку дилера, а
дальше порядок мест по кругу даёт и блайнды, и позицию. Круг проверен по
записи: на шести разных положениях кнопки малый блайнд каждый раз оказывался
на следующем месте, а большой — на втором. Отдельного правила для стола на
двоих не понадобилось: там «второе место» заворачивается обратно на кнопку, и
общее правило само даёт верный ответ — вдвоём большой блайнд ставит дилер, и
ходит он последним на всех улицах.

Позиция берётся один раз за раздачу и дальше не пересчитывается: считается она
по тем, у кого ещё есть карты, а люди из раздачи выбывают. Пересчитанная после
чужого фолда, она превратила бы большой блайнд в малый. Размер блайндов,
наоборот, живёт дольше раздачи — за столом он не меняется, а чистое начало
раздачи видно не на каждом кадре.

Ставить и повышать — разные кнопки, и путать их нельзя: пока доплаты нет,
игра рисует `CHECK` и `BET`, а кнопки `RAISE` на экране просто не существует.
Совет «рейз» там отправлял искать то, чего нет.

**Размер помощник называет кнопкой, а не только числом.** Над кнопками хода
игра держит ряд готовых размеров — `MIN`, `3 BB`, `BANK`, `ALL IN`, — и это
одно нажатие вместо ползунка, который иначе ведут мышкой на
пятнадцатисекундном таймере. Сколько ставит каждая, считает `quick_bets()` в
`poker_math.py` из того, что зрение уже читает: минимум с кнопки повышения,
блайнды, банк, стек. Какую нажать — до флопа выбирается по близости к размеру
из таблицы открытия, с округлением вверх, а после флопа считается выгода
каждой: чем больше просим доплатить, тем чаще все пасуют и тем уже те, кто
ответит. Не подошла ни одна — совет остаётся числом для ползунка, как раньше.

**Совет говорит и о том, что будет дальше.** Одно слово «чек» не отвечало на
главный вопрос: фишки уходят не на чеке, а на том, что случается сразу после
него — соперник ставит, и решать приходится заново. Теперь под советом стоит
строка на ход вперёд: «если поставит: доплата до 1 000 — колл, крупнее —
фолд», «если поставит — фолд», «если повысит: доплата до 2 000 — рейз, весь
стек — колл». Считается тем же движком: совет прогоняется ещё раз по лесенке
размеров, которыми соперник может ответить — треть банка, две трети, банк
целиком и наш стек, — и лесенка читается до первого «фолда», потому что
заплатить крупную ставку, сбросив мелкую, — не план, а путаница. Правило у
плана и у живого совета общее (`call_or_raise`), иначе план обещал бы одно, а
через кадр экран советовал бы другое. Числом в плане называется доплата, а не
своя ставка: «до 2 000» соседней строкой уже означает размер собственного
повышения, и одно «до» не может значить в одном окне две разные вещи.

До флопа границы в плане нет, и это не упущение: там отвечает таблица, а она
смотрит на руку и позицию, а не на размер чужого повышения. Ответ у неё один
на любой размер — «если повысит — колл», «фолд» или «повышаем в ответ».

Доля отвечающих считается непрерывно — `банк / (банк + ставка)`, минимальная
защита, — и это не эстетика. На трёх ступенях «маленькая ставка, большая,
олл-ин» ставка в банк и олл-ин на десять банков попадают в одну ступень, а
денег на олл-ине уходит больше: помощник советовал `ALL IN` вообще с любой
рукой, которой стоит ставить. Сверху стоит потолок в два банка: даже с
непрерывной моделью одноуличный счёт любит оверставки, а живой человек на
ставку в три банка просто пасует, и за флопом ещё идут тёрн и ривер.

`kisiki/modules/poker_vision.py` читает кадр за 18–26 мс: общие карты, свои
карты, своё место из шести, число участников раздачи, банк, горшки, ставки на
сукне, свой стек, сумму на кнопке `CALL`, сумму на кнопке `BET` / `RAISE` и
признак «ход мой». Оба модуля не создают окон и проверяются на кадрах из
`tests/fixtures/poker/`.

Разряды игра делит пробелом, и по последнему куску надписи `CALL 1 250`
читалось как 250 — впятеро дешевле настоящего колла. На обычной кнопке сумма
написана малиновым, а слово чёрным, поэтому все знаки маски и есть число; на
залитой кнопке белым написано и слово, и сумма, и тогда слово — первый кусок,
а всё после него склеивается в одно число.

Банк считается по двум местам сразу: плашка «Общий банк» не включает ставки
текущей улицы, а на префлопе её нет вовсе — блайнды лежат перед игроками. По
одной плашке шансы банка выходили завышенными, а до флопа помощник просто
молчал.

Когда за столом олл-ин на меньшую сумму, банк раскладывается по горшкам, и
игра рисует их полосой под бордом. Прибавлять их к «Общему банку» нельзя:
плашка над бордом — это уже их сумма, и на пяти случаях из двух записей она
сошлась с полосой знак в знак. Зато полоса даёт банку второй счёт: пока
анимация сгребает фишки, плашка отстаёт — 9 842 при настоящих 13 000, — и по
расхождению видно, что этому банку сейчас верить нельзя. Она же чинит
доплату: перед ушедшим в олл-ин лежит вся его ставка, уравнивать её не надо,
и счёт по сукну требовал доплатить 1 000 там, где игра пишет `CHECK`. При
разложенном банке доплата берётся только с кнопки. А какой из горшков наш,
помощник не считает — для этого надо знать, сколько внёс каждый, — и честно
пишет на экране, что банк разложен.

Кнопка хода под курсором мыши заливается малиновым, и текст на ней белеет.
Разбор такой кнопки — отдельная работа: сумма ищется по строке, а курсор,
накрывший цифру, чтение отменяет. Иначе «CALL 250» читается как «2».

Доплату помощник считает дважды: с кнопки и по ставкам на сукне, где она
равна старшей ставке минус своя. На трёх записях два счёта сошлись на 1089
кадрах из 1090, а в сотне кадров ставки ответили там, где кнопку закрывал
курсор. Расходятся — экран молчит: гадать, какой из двух счётов верный,
не на чем.

Ставку своего места помощник искал широкой рамкой — и на верхнем левом месте
ловил в неё чужое: под панелью игрока игра рисует меню «ПОКУПКА ЗА ⊙», и его
золотая кнопка стоит вплотную к плашке ставки. Своя ставка 250 читалась как
2501, а пустое место — как «не разобрал»; два счёта доплаты расходились, и
экран молчал всю раздачу. Теперь рамка узкая, срезанные её краем пятна за
фишку не считаются, а знаки числа отбираются по общей строке: круглая кнопка
«$» из того же меню выше цифр и в сумму не попадает. На записи, где игрок
сидел сверху слева, подсказка появилась на 62 кадрах своего хода из 63 —
раньше их было 51.

Минимум, который игра примет, написан на кнопке `BET` / `RAISE`: ползунок
ниже него не опускается. Но только пока бегунок стоит у левого края — стоит
его подвинуть, и на кнопке уже не минимум, а выбранный размер. Бегунок в
покое занимает пять процентов дорожки, один шаг сдвигает его ещё на три, и
порог взят посередине: иначе подвинутый на шаг ползунок сошёл бы за
нетронутый и «минимумом» оказалось бы вдвое большее число.

**Минимум проверяется трижды, и не зря.** Он работает полом для всех четырёх
быстрых кнопок, поэтому одно неверное число ломает не размер, а сам ход: на
кадре из записи `8.mp4` курсор сел на цифру надписи `RAISE 4 000`, минимум
прочитался как 654 000, все кнопки подтянулись к нему, обрезались стеком и
схлопнулись в одну — и совет вместо «жми MIN, 4 000» сказал «жми ALL IN,
поднять до 84 000» при банке 12 000. Теперь `sane_minimum()` отбрасывает то,
чего игра показать не могла (выше стека и выше удвоенной старшей ставки —
минимальное повышение больше этого не бывает), `quick_bets()` не даёт минимуму
съесть остальные кнопки, а память берёт его со второго одинакового кадра:
настоящий минимум стоит на кнопке всю улицу, а мигнувший не стоит ничего.

Блайнды читаются только до флопа. После него ставка и ответное повышение
складываются в ту же картинку — две ставки, старшая вдвое больше младшей, — и
на записи `8.mp4` блайнды прочитались как 3 500 / 7 000 при настоящих
250 / 500. Глубина стека после этого выходила 4 ставки вместо шестидесяти,
префлоп уходил в режим «олл-ин или пас», и помощник три раздачи подряд
советовал ва-банк. Блайнды на сукне видны только на чистом начале раздачи, и
непустой борд отменяет чтение целиком.

**Журнал раздач.** `kisiki/modules/poker_journal.py` записывает, что сыграно,
чем кончилось и сколько это стоило: свою руку, позицию, борд, банк, результат
в фишках, чужие руки, дошедшие до вскрытия, и чужие ходы из строки событий. Отсюда BB/100 и сравнение
периодов — «+21 BB/100 за последние 50, −7 до них». Без этой пары чисел спор
«стало лучше или просто повезло» решается на глаз и повторяется после каждой
записи.

Победителя игра отмечает залитой золотом плашкой `WIN` справа от его панели, и
по ней журнал считает раздачи. Просто по золоту её не найти: сукно расписано
жёлтым, и логотип «PLAY» лежит ровно под нижним правым местом. Отличается
метка тем, что залита целиком, — маска съедается эрозией, тонкие линии
разметки исчезают начисто, а от метки остаётся три четверти. На вскрытии
заодно читаются чужие открытые руки: другого способа узнать, с чем за этими
столами доходят до конца, нет.

**Чужие ходы приходят из строки событий.** Игра сама пишет в левом нижнем
углу, кто что сделал: «Sven Montana повысил до 100 фишек», «Gerogen Montana
пропустил ход». Читать это надёжнее, чем сравнивать кадры между собой, — при
четырёх кадрах в секунду быстрый фолд теряется, а дырявый журнал для
статистики хуже, чем никакого.

Строка разбирается по цвету: имя игрока написано малиновым, время и действие —
серым, ровно как на кнопке хода сумма отделена от слова. Само действие
узнаётся по первому слову — их всего девять, и они нарезаны эталонами в
`poker_words.png`: «пропустил», «уровнял», «поставил», «повысил», «сбросил»,
«выиграл», «передана», «Началась», «Игра». Разные слова похожи друг на друга
не больше чем на 0,48, а своё узнаётся в среднем на 0,88. Имя не читается
вовсе — от него берётся отпечаток: узнавать, что это тот же человек, нужно, а
разбирать буквы переменной ширины — отдельный большой проект.

Журнал игра держит свёрнутым, и свёрнутая строка гаснет через пару секунд —
прочитать по ней ход нельзя. Развёрнутый журнал показывает десять строк и не
гаснет; экран пишет об этом прямо, потому что иначе игрок будет думать, что
статистика копится. Одни и те же строки приходят с каждым кадром, пока журнал
не прокрутится, поэтому записанное помнится по отметке времени, а одинаковые
события одной секунды считаются по тому, сколько раз строка встретилась в
самом окне.

К раздаче ходы приписываются по времени, а не по строке «Началась новая игра»:
её игра пишет с опозданием, и на кадре с уже розданными картами этой строки
ещё нет. Пока границей была она, в журнал уходили ходы **прошлой** раздачи —
со своими ставками и своим банком, но с чужими картами в записи. Отметка
начала всё равно в деле: если она в окно попала, всё, что было до неё,
отрезается как хвост прошлой раздачи. И собираются ходы до последнего
момента — не на кадре, где раздача закрылась, а когда её пишут в журнал:
строка «выиграл N фишек» приходит уже над пустым столом.

**Замер по журналу.** `kisiki/modules/poker_stats.py` складывает из чужих
ходов то самое число, которым модель размера пока пользуется из теории:
сколько за этим столом платят на ставку в полбанка, в банк и больше банка.
Банк по ходам приходится восстанавливать — в самих строках его нет, — и
сходится он со строкой «выиграл N фишек» той же раздачи; на этом сверка и
держится. Префлоп считается отдельно от постфлопа: до флопа открывают в
четыре-двадцать блайндов при банке в полторы ставки, и в долях банка такая
ставка вдесятеро крупнее любой постфлопной. Результат стоит на экране в
панели «ЖУРНАЛ», в одной строке с числом записанных ходов — и только тогда,
когда ответов набралось достаточно: число, посчитанное по трём раздачам, там
хуже честного «мало». Одной строкой, а не двумя, потому что панели при окне
1040 × 860 достаётся 167 пикселей: лишняя строка обрезала ту, что просит
развернуть строку событий, — самую нужную из четырёх.

Результат раздачи меряется по стеку **между** раздачами, а не внутри неё:
только там банк уже сгребли, а блайнды следующей ещё не поставили. Мерка от
первого кадра раздачи теряла бы свой блайнд — на шести местах это 25 BB/100,
больше, чем весь выигрыш, который тут вообще меряют. Покупку фишек между
раздачами от выигрыша по стеку не отличить, поэтому стоит проверка: выиграть
больше, чем лежало в банке, нельзя. Не сошлось — раздача идёт в журнал без
результата, и экран честно пишет «в счёте 12 из 13». И раздачи, начала которых
помощник не видел, не считаются вовсе: севший смотреть посреди раздачи не
знает, сколько уже ушло из стека в банк.

Меряется он не на любом кадре паузы, а на устоявшемся. Банк едет к победителю
секунду с лишним после того, как стол опустел, и каждый кадр анимации
показывает новое число — на записи `8.mp4` в панели стояло «121» при настоящих
29 500. Поэтому в счёт идёт стек, повторившийся два кадра подряд:
промежуточные значения не повторяются, а досчитанный держится до самой
раздачи. Раздача закрывается раньше, чем анимация кончается, и ждёт своего
результата в памяти — не дождалась к началу следующей, значит результата у неё
нет. Ноль в паузе при этом настоящий: у проигравшего весь стек фишек и правда
не осталось, и раздача за весь стек стоит ровно столько, сколько стоила. До
этой правки в журнал уходили числа вроде −43 879, −232 и +6 297 — все из
середины анимации.

`poker.py` смотрит на экран четыре раза в секунду и помнит то, чего на одном
кадре не видно: своё место, свои карты, борд, банк, горшки, доплату, свою
ставку, стек и границы раздачи. `F9` — начать смотреть или пауза, `F11` —
остановиться. Из `core.py`
экран берёт только поиск окна и границы клиентской области: `send_key_tap`,
`send_left_click` и `activate_window` сюда не импортированы, и это
проверяется тестом.

Память нужна против одиночных плохих кадров: карту закрывает рука дилера,
между улицами стол на миг пустеет, курсор накрывает сумму. Раздача считается
законченной только после трёх пустых кадров подряд, а новой — когда сменились
свои карты или борд.

Своё место внутри раздачи заперто. Оно ищется по единственной открытой руке,
а когда своя рука уже сброшена и до вскрытия дошёл один соперник, его карты
лежат лицом ровно так же — и помощник считал бы чужую руку своей. Пересесть
можно между раздачами, и лишь там замок снимается.

Замок снимается не сразу: пока горит метка `WIN`, место не перечитывается
вовсе. Стол пустеет не разом — карты убирают раньше борда, — и в эту щель
влезала «новая раздача»: помощник объявлял своим место соседа, показывал его
карты своей рукой и записывал её в журнал отдельной раздачей. В журнале с
записи `8.mp4` таких двойников две пары: один борд, три секунды разницы,
чужая рука. Поэтому же раздача считается начатой только с пустого борда — с
него она и начинается, а карты вскрытия начинать нечего.

Помощник молчит, когда считать не по чему: не видит своих карт, не разобрал
доплату, не знает, сколько денег на столе, идёт вскрытие или ход не твой.
Честное «жду» лучше уверенной чуши — без банка шансы банка выходят
стопроцентными, и совет всегда получался бы «фолд».

Процент, который игра рисует сама («A СТАРШАЯ КАРТА 14 %»), для решений не
годится: это сила уже собранной комбинации, а не шанс выиграть. Флеш-дро игра
оценивает в 18 % там, где настоящее эквити 61 %.

Задумка отличается от остальных модулей-лудоманов: покер — игра с неполной
информацией и живым соперником, поэтому автопилота здесь не будет. Помощник
читает стол и подсказывает, а нажимает кнопки человек.

Разбор вариантов, замеренная геометрия интерфейса, опорные кадры и **план
дальнейших работ** собраны в `poker-plan/README.md`. Порядок пунктов там не
случайный и объяснён на месте: браться за следующую задачу по покеру стоит
оттуда, а не с чистого листа.


## Требования к ресурсам

Иконки грузятся через `rounded_photo()` в `kisiki/core.py` и уменьшаются
целочисленным `subsample`, поэтому исходники должны быть заметно крупнее
экранного размера.

- **Котики** — `assets/cats/NN_name.png`, порядок и имена задаются в `CATS`.
- **Еда** — `assets/food/NN_name.png`, ровно 20 штук, имена должны совпадать
  с `FOOD_CATALOG` в `food_catalog.py`: по ним работают рецепты.
- **Руда** — `assets/ores/NN_key.png`, имена соответствуют `ORE_TYPES` в
  `kisiki/modules/miner_vision.py`.
- **Эталоны зрения** — `assets/vision/`; файл `race_odds_2_1.png` нужен
  RACE BETTOR для распознавания коэффициента, а `blackjack_digits.png` —
  BLACKJACK RUN для чтения счёта руки. Оба должны попадать в сборку.
  `poker_ranks.png` (13 знаков ранга), `poker_suits.png` (4 масти),
  `poker_digits.png` (10 цифр) и `poker_words.png` (13 слов строки событий)
  нарезаны из кадров покерного стола, их читает `poker_vision.py`. Вместе они
  весят 6 КБ.

Общие правила для игровых иконок котиков, еды и руды:

- `PNG`, RGBA, прозрачный фон, без анимации.
- Пиксель-арт в едином стиле: крупные чёткие пиксели, без размытия,
  антиалиасинга, градиентов и полупрозрачных краёв. Масштабировать только
  nearest-neighbor.
- Предмет занимает 75–85% холста, по центру, не обрезан.
- Без рамок, фоновых квадратов, текста, подписей, эмодзи и водяных знаков:
  фон карточки приложение рисует само.
- Одинаковые у всех: размер пикселя, толщина обводки, направление света,
  ограниченная палитра. Допустима ступенчатая тень в 1–2 оттенка.
- Образ должен читаться в мелком размере — еда и руда показываются с 38 px,
  котики с 54 px.
- У каждого предмета внутри набора свой доминирующий цвет: в рецептах двадцать
  блюд стоят рядом иконками по 38 px, и похожие силуэты должны различаться
  хотя бы по цвету.

Размер исходника выбирается не «побольше», а под `rounded_photo()`: она
уменьшает только целочисленным `subsample`, то есть берёт каждый N-й пиксель
без усреднения. Слишком крупный исходник от этого не выигрывает, а проигрывает
— мелкие детали превращаются в кашу.

Котики лежат **484 × 484 px** (~250 КБ): при таком размере все четыре
экранных размера из `CAT_IMAGE_SIZES` получаются кратным делением почти без
остатка. Раньше они были 1254 × 1254 и весили под мегабайт — картинка на
экране от этого была не лучше, а хуже, зато `.exe` толще на 9 МБ. Оригиналы
до уменьшения лежат в `assets/cats_src/` и в сборку не попадают.

Еда и руда показываются с 38 px, им хватает **256 × 256 px** и 150 КБ.

**Звук.** У каждого котика свой звук по его индексу в `CATS` — список
`SOUND_FILES` в `kisiki/core.py`. Список может быть короче `CATS`: котику без
своего звука `cat_sound()` отдаёт `PLACEHOLDER_SOUND`, поэтому нового котика
можно добавить, не подбирая ему звук сразу. Чтобы дать свой — положите файл в
`sounds/` и впишите его в `SOUND_FILES` на позицию этого котика.

Генераторы `make_meme_sounds.py` (`.wav`-заглушки) и `make_orange_icon.py`
(иконка приложения) разовые и в рантайме не участвуют.

## Тесты

```powershell
python -m unittest discover -s tests -v
```

Сейчас 536 тестов. Отдельный файл запускается только с корнем проекта в
`PYTHONPATH`, иначе не найдётся пакет `kisiki`:

```powershell
$env:PYTHONPATH = $PWD; python tests\test_miner.py
```

Кадры для тестов зрения лежат в `tests/fixtures/miner/`. Видеозаписи `*.mp4`
из этой папки намеренно не попадают в git: они нужны только для ручного
разбора и весят гигабайты. Проверки RACE BETTOR создают синтетические кадры
во время запуска, поэтому пользовательские скриншоты скачек в проекте не
хранятся.

## Сборка

```powershell
python -m PyInstaller --noconfirm build_kisiki.spec
```

Результат — однофайловый `dist/Kisikisimyaumyau.exe`. Имя латиницей не
случайно: GitHub заменяет кириллицу в именах файлов-вложений точками, и
`Кисикисимяумяу.exe` человек скачал бы под именем из одних точек. Заголовок
окна задаётся отдельно в `app.py` и остаётся русским. Список упаковываемых
ресурсов задаётся в `datas` внутри `build_kisiki.spec`: добавили новую папку
с картинками — впишите её туда, иначе в собранном приложении иконок не будет.

Из сборки намеренно выброшен `opencv_videoio_ffmpeg*.dll` — это 12 МБ
видеокодеков, а приложение только снимает экран и разбирает кадры: ни
`VideoCapture`, ни `imshow` в коде нет. Если когда-нибудь понадобится читать
`.mp4` прямо из приложения, строку-фильтр в спеке надо будет убрать.

## Релиз

`.exe` самодостаточен: ни Python, ни библиотек ставить не нужно, прогресс
пишется в `%LOCALAPPDATA%`. Но сборки **не коммитятся в git** — каждая
добавляла в историю ~80 МБ, а GitHub вообще не принимает файлы тяжелее
100 МБ. Поэтому `dist/` лежит в `.gitignore`, а готовый `.exe` выкладывается
в **GitHub Releases**: отдельное хранилище, до 2 ГБ на файл, клон
репозитория от этого не пухнет.

Порядок выпуска новой версии:

1. **Прогнать тесты.** Красные тесты в релиз не уезжают.

   ```powershell
   python -m unittest discover -s tests
   ```

2. **Собрать.**

   ```powershell
   python -m PyInstaller --noconfirm build_kisiki.spec
   ```

3. **Поставить тег** на коммит, из которого собирали, и отправить его. Без
   тега на GitHub форма релиза ругается «Make sure you have a valid tag».

   ```powershell
   git tag -a v1.1 -m "Короткое описание версии"; git push origin v1.1
   ```

4. **Создать релиз** на `github.com/<...>/releases/new`: выбрать в поле Tag
   уже отправленный тег, написать заголовок и описание, перетащить
   `dist/Kisikisimyaumyau.exe` в Attach binaries, нажать **Publish release**.
   Пока не нажата эта кнопка, релиз остаётся черновиком и виден только
   автору.

5. **Проверить, что залилось целиком** — размер в ответе должен совпадать с
   размером локального файла.

   ```powershell
   (Invoke-RestMethod "https://api.github.com/repos/<владелец>/<репозиторий>/releases/tags/v1.1").assets |
       Select-Object name, size, state
   ```

Ссылка на прямое скачивание собирается из тега и имени файла:
`https://github.com/<владелец>/<репозиторий>/releases/download/v1.1/Kisikisimyaumyau.exe`

Чего ждать тому, кому отдали файл: неподписанный `.exe` показывает окно
SmartScreen («Подробнее» → «Выполнить в любом случае»), а антивирусы иногда
ругаются — программа шлёт нажатия клавиш и снимает экран, для эвристики это
выглядит подозрительно. Лечится только подписью сертификатом, а она платная.

### Если история всё-таки распухла

Так уже было: `.exe` коммитился и оставил в истории четыре копии на 287 МБ,
репозиторий весил 524 МБ. Вычищается `git-filter-repo` (`pip install
git-filter-repo`), но это переписывание истории — сначала бэкап
(`git bundle create ../backup.bundle --all`), потом:

```powershell
git filter-repo --path dist --invert-paths --force
git remote add origin <адрес репозитория>
git push --force origin main
```

`filter-repo` штатно удаляет remote, поэтому его возвращаем вручную.

## Данные игрока

Прогресс хранится вне проекта:

```text
%LOCALAPPDATA%\KisikiSimyaumyau\progress.json
%LOCALAPPDATA%\KisikiSimyaumyau\poker_journal.json
```

Журнал покерных раздач лежит отдельным файлом нарочно: прогресс кликера
читается на каждом запуске, а раздач за вечер набегают сотни. Держится в нём
две тысячи последних, сломанный файл читается как пустой журнал — статистика
не стоит упавшего экрана посреди раздачи.

Журнал, записанный до того, как разбор кадра починили, чинится разово:

```powershell
python clean_poker_journal.py
```

Скрипт выбрасывает раздачи-двойники (карты вскрытия начинали «новую раздачу»),
возвращает блайнд, прочитанный с постфлопной ставки, и округляет до фишки
результаты, пойманные посреди анимации. Старый файл остаётся рядом как
`poker_journal.bak.json`: журнал — единственные данные, которых нет больше
нигде. На журнале с записи `8.mp4` это две раздачи, три блайнда и четыре
результата из шестидесяти пяти.

Удаление файла прогресса начинает игру заново. `KisikiApp.load_game()` не мигрирует
сохранения, а собирает их поверх `fresh_game()`: каждое поле читается
отдельно и с запасным значением, поэтому старый или битый файл не роняет
игру, а теряет только незнакомые поля. Поле `version` сейчас записывается,
но при чтении не используется — если понадобятся настоящие миграции,
разбирать его нужно именно в `load_game()`.

## Подводные камни

- **`CTkScrollbar` заставляет перерисовывать окно.** Его `_draw()`
  заканчивается вызовом `update_idletasks()`, поэтому каждый виджет,
  добавленный в `CTkScrollableFrame`, вызывает полную перерисовку. Из-за
  этого экраны мерцали при сборке. Лечится тем, что `KisikiApp.clear()`
  прячет контейнер на время построения экрана и возвращает его через `after`
  — таймерное событие переживает чужие `update_idletasks`, а `after_idle`
  показал бы недособранный экран.
- **Каждый размер картинки режется отдельно.** Кеш в `KisikiApp.photo()`
  живёт по ключу «картинка + размер». Новые размеры нужно добавлять в
  `CAT_IMAGE_SIZES` / `FOOD_IMAGE_SIZES` в `kisiki/app.py`, иначе фоновый
  прогрев их пропустит и экран один раз распакует PNG сам.
- **`.exe` в git не коммитится.** Так было раньше, и это стоило 287 МБ в
  четырёх копиях: репозиторий распух до 524 МБ, а GitHub вообще не принимает
  файлы тяжелее 100 МБ. Теперь `dist/` целиком в `.gitignore`, сборки
  раздаются через Releases.
